# Route → target index

Every user-facing route in `apps/westayfit/app/`, mapped to the visual target
that covers it. Generated by reading the route tree at the branch head, not from
memory.

**This index is inventory, not design.** It says what exists and what does not.

**The owner boards are in the repository and are the north star.** Open both
before every target-design pass and before every implementation pass:

```

docs/design-target/owner-north-star/OWNER-BOARD-2-after-target-wsf-vision.png
```

**Atlas-first is the current gate.** An earlier revision of this file said the
atlas was "the coverage register, not an implementation blocker". That is
superseded: the owner's instruction and the committed
`THREAD-CONTINUATION-BRIEF-2026-09-21.md` both require the missing atlas to be
finished and visually reviewed **before any further page implementation**.
**That gate is now cleared.** The atlas was reviewed and accepted as target
reference on 2026-09-21. Pages 1–5 all keep their recorded acceptance,
including Page 5 (`/you`), which was implemented under its own separate owner
instruction and accepted. **Batch A** was likewise authorized separately and
is implemented, awaiting visual/functional review.

**Acceptance of a batch authorizes nothing to be built.** Batches B–G are
accepted as target reference and remain drawings.

**The page-level visual gate still stands**, on every page:
ACTUAL BEFORE → reviewed TARGET → ACTUAL AFTER → visual acceptance.

**Target existence is not visual acceptance.** Four states are tracked
separately and must not be conflated: a target **exists**, a target is
**reviewed**, a route is **implemented**, and an implementation is
**verified**.

Where each batch stands against those four: **A–G are reviewed** and accepted
as target reference. **Batch A is also implemented**, under its own separate
owner instruction, and is under review — not yet verified. **B–G are drawn and
reviewed and nothing more**; being accepted as reference authorizes none of
them to be built.

## Coverage today

**The route tree is computed, and so are the tables below it.** The script
walks `apps/westayfit/app`, derives every route from the file tree, and checks
each against a target registry and an implemented-list kept inside the script
itself. It does **not** discover target files on disk, so keeping that registry
honest is still a person's job — but the document no longer restates what the
script already knows.

```
node scripts/westayfit/route-target-coverage.mjs            # the report
node scripts/westayfit/route-target-coverage.mjs --write    # regenerate the tables below
npm run wsf:route-coverage -- --check                       # fail if they have drifted
```

Two hand-maintained tables used to live here, and both rotted. The counts in
this section drifted to `4` implemented while the register said `5`, and
`/community`, `/activity` and `/you` each appeared in the covered table **and**
in the not-covered table at the same time, because a covered row was added as
each page shipped and the matching uncovered row was never pruned. Both tables
are generated now, between markers, and `--check` fails if they and the route
tree disagree.

**That gap is closed.** It used to read here that of the six device classes the
atlas requires — 390x844, 390x640, 430x932, 800x1280 tablet portrait, 1280x800
tablet landscape and 1920x1080 collective display — only the three phone sizes
had any target at all. All six are now drawn, and the generated
`ATLAS-COVERAGE.md` device tally is the authority rather than this sentence:
1280x800 in Batches E, F and G, 800x1280 in E and F, 1920x1080 in F and the
physical-flow board.

**Drawn is not built.** Those three larger classes are **target reference
only** — no kiosk, station or display route was implemented, and the frame
counts anywhere in these documents describe drawings, never implementation and
never verification.

`/design-target/*` (gated preview routes) and `/health` are excluded: the first
are not member surfaces and cannot be served by a deployed artifact, and the
second is operational.
