## 3. Turn A — scope (one turn, gate green, staging redeploy)

**A1. `wsfMyCommunities` callable** (auth required, no rules change). Reads
`wsfMemberships` where `userId == uid` and `membershipStatus == 'active'` with the Admin
SDK, loads each group, and for each active challenge returns the aggregate totals only.
Response items: `{ groupId, displayName, groupType, joinPolicy, role, memberCount,
activeChallenge: { id, title, participantCount, completedCount, goalTarget } | null }`.
Excludes `isSample` groups from nothing here (a member of a sample group still sees it,
marked `isSample: true` in the item so the UI can badge it "Sample"). Never returns other
members' identities.

**A2. Signed-in home on `/`.** When `ready && user`: eyebrow, "Your communities" list from
A1 (card: name, type label, place label if any, role label, active challenge title with
"N moving · M check-ins" or "No active challenge yet"), each card links to
`/community/<id>`; below it "Start a community" (primary) and "Join with a code" (text
field → `/join/<code>`, validated with the same shape as `pendingJoinCode.ts`); a Sign out
link; display name shown. Empty state when no memberships: "You're not in a community yet"
with the same two actions. Signed-out `/` keeps the chartered lines and adds the same
"Join with a code" field under the two buttons. The `Build details` link moves to the
bottom in small text. Loading and error states are explicit (`data-state`).

**A3. Routing.** `signin.tsx`: after sign-in, if unverified → `/verify-email`; else read
`wsfMemberProfiles/{uid}` — exists → `nextRouteAfterAuth('/')`, missing →
`nextRouteAfterAuth('/profile-setup')`. `verify-email.tsx`: same profile check after the
token refresh. `profile-setup.tsx`: on mount, if the profile already exists and the route
has no `?edit=1`, `router.replace(nextRouteAfterAuth('/'))`; after a successful save go to
`nextRouteAfterAuth('/')` (the home shows Start/Join). `start-community.tsx` and the
community page: unchanged guards.

**A4. Profile-setup.** Remove the 18+ checkbox and the `adultConfirmation` field write.
Write with create-or-update semantics: on create set `createdAt`; on update never touch
`createdAt` or the accepted versions unless the version changed. Keep one acceptance
checkbox whose label reads: "By saving I confirm I am 13 or older and accept the Terms of
Service and Privacy Policy." The words *Terms of Service* and *Privacy Policy* are tappable
and expand inline panels (accordion, `accessibilityRole="button"`, `aria-expanded`) that
render `apps/westayfit/legal/terms.md` and `apps/westayfit/legal/privacy.md` as plain
text with headings. Those two files ship with exactly this content until Devin supplies
approved text: the title, the line `Version pending-approval-2026-08-25`, and the sentence
"This text is pending approval and will be replaced before public launch." The
`profileConstants.ts` versions stay as they are.

**A5. Server guards.** Remove the `adultConfirmation !== true` checks from
`wsfCreateCommunity` and `wsfJoinCommunity`. Keep the "profile must exist" checks.
Callable tests updated: a profile without `adultConfirmation` can create and join.

**A6. Community page.** Human labels via one shared `src/labels.ts`
(`groupTypeLabel`, `joinPolicyLabel`, `roleLabel`, `statusLabel`): Founding Champion,
Co-Champion, Member; Active, Paused, Archived; Family and friends / Something else (turn B
extends the map). Add: a members count line ("4 members" from A1 or a count query through
the callable), an **Invite** section when `joinPolicy === 'public'` — the join URL built
from `window.location.origin` + `/join/<joinCode>` with a Copy button (clipboard API with a
"Copied" state) and the native share sheet when `navigator.share` exists; for `private` and
`inviteOnly` show "Invite links arrive with the next update" (turn B). When there is no
active challenge show a card "No challenge running yet" with the sentence "Starting a
challenge from the app is coming next" — no dead buttons. The challenge link becomes a card
with the title and the shared number from `wsfListChallenge`.

**A7. Start-community.** Add the third join policy `public` with the copy: **Public** —
"Anyone can find and join"; **Anyone with the link** (`inviteOnly`); **Private** — "I add
each member". Default stays `private` for Family and friends and becomes `inviteOnly` for
Something else. Show the join-policy description under the pills. The server already
accepts `public`.

**A8. In-app-browser hint.** `src/inAppBrowser.ts`: `isInAppBrowser()` = user agent matches
`/Instagram|FBAN|FBAV|FB_IAB|Messenger|Line\/|TikTok|Snapchat|Twitter/i`. When true, every
screen shows a dismissible banner under the eyebrow: "You're in Instagram's browser, so you
may be signed out next time. Tap the ··· menu and choose *Open in browser* to stay signed
in." Dismissal is remembered in `sessionStorage` only.

**A9. Tests and gate.** `tests-e2e/mu2-flow.spec.ts` updated (no 18+ checkbox; profile →
home; the community appears on the home; re-sign-in lands on the home with the community
listed, not on profile-setup; the community page shows "Founding Champion" and "Active";
the selected join policy equals the stored one — F9). New `tests-e2e/e35-home.spec.ts`
(signed-out landing with the code field; signed-in home with a membership card; join-with-
code → `/join/<code>`; in-app banner with a UA override; terms accordion expands and shows
the version line). Callable tests for `wsfMyCommunities` (member sees own groups with
aggregate totals only; non-member sees nothing; sample group badged) and for the removed
guards. `gate1.sh` adds the new spec. Then: build (auth flag ON, no emulator flag), deploy
`functions:westayfit`, `hosting:channel:deploy staging`, functions:list diff, smoke, and
the report.

## 5. E4 proposal for Devin — the general-product surface

This is what "the main page doesn't have a lot on it" really asks for. It is the M-U5 /
M-U6 work that the FitLife reduction cut; it needs Devin's sequencing against E4 counters,
E5 pulse view and E6 expo hardening.

1. **Find a community.** `wsfSearchCommunities` (public invoker, per-IP limited like the
   pulse): `where joinPolicy == 'public' && lifecycleStatus == 'active' && isSample == false`,
   in-memory case-insensitive match on name and place label, limit 20, returns name, type,
   place label, member count, join URL. No index, no rules change. Search box on the
   landing and on the signed-in home.
2. **Landing = two doors.** "Start a community" and "Join one near you" (search + code),
   the chartered lines, a truthful aggregate line ("12 communities moving · 340 check-ins
   this week", samples excluded, hidden below a floor of 3), and the three-step loop
   (start → challenge → invite → move together). Lower-page GoArrive sentence per master §2.
3. **Champion starts a challenge** from approved starter templates (`wsfChallengeTemplates`,
   staff-curated, `isApproved`): pick, name, optional goal → `wsfStartChallenge` creates the
   challenge and its moves for the group. This is M-U4's first half and the one thing that
   makes a freshly created community usable without a seed script.
4. **Community page as the operating page** (M-U5): members count, active challenge card
   with the shared number, invite link + QR, Champion controls (pause challenge, edit name,
   change join policy), all aggregate, no member directory by default.
