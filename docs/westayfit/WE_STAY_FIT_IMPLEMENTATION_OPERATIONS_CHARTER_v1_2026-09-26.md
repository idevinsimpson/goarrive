# WE STAY FIT — Implementation and Operations Charter
Version 1.0 | September 26, 2026
Status: owner-authorized replacement for the September 11 working implementation plan v0.2

This document governs execution sequencing and evidence discipline. It does not replace Strategic Master v3.0 + v3.1, and it does not itself authorize production release, spending, legal approval, new data collection, or public publishing.

## 1. Delivery objective

Deliver a coherent WSF member product in which:
- a person reaches the right community;
- understands the current goal and what counts;
- starts or joins without being forced into organization/sales/coaching work;
- completes an approved contribution flow;
- receives exact own credit and truthful shared state;
- sees the Living WE change only from confirmed progress;
- returns to useful community context;
- experiences the community as inhabited without rankings or privacy leakage;
- can continue after a goal through honest history and the next real opportunity.

LIVE reuses that same truth on phone, kiosk/station, and public display.

## 2. Current implementation model

### Canonical product
Authenticated WSF product: `apps/westayfit` + `functions-westayfit` + Firebase.

### Public marketing
Separate Lovable/Supabase marketing/inquiry surface.

### North Star
Separate WE Community Home Lovable project plus accepted owner boards/route targets. It supplies visual/interaction reference, not production data authority.

### Development vs operations
- Canonical development carries accepted/integrated product work.
- Operational `main` carries the reviewed staging control plane and approved staging pointer.
- Served staging is established only by deployment/marker receipts.
- Production is separately authorized.

## 3. Product surfaces and current direction

### Home

### LIVE
Phone complete participation; optional shared kiosk/station; separate public display; exact cross-device state; session/reset/privacy/recovery proof required.

## 4. North Star packet contract

No new member-visible implementation packet is READY until it freezes:
- exact journey;
- project/target reference and SHA;
- required states;
- viewport evidence;
- source donors or explicit absence;
- accepted truth/platform differences;
- navigation/focus/motion/reduced-motion expectations;
- reserved canonical files.

The implementer returns matched AFTER evidence, not only source/tests.

## 5. Execution priority

Default priority:
1. truthful, usable contribution-to-Living-WE loop;
2. current visible member North Star parity;
3. identity/join/start continuity required to reach that loop;
4. authenticated community presence/privacy;
5. lifecycle/history/continuation;
6. LIVE cross-device reliability;
7. release/recovery hardening;
8. scale/performance work when measurements show member/release impact;
9. later administration, automation, monetization, physical-marker expansion.

A control-plane/scale task may preempt visible work only when it blocks truth, privacy, data integrity, cross-device behavior, or release safety.

## 6. Worker model

Use the Fable operating protocol and current worker-inbox map.

Rules:
- one implementation owner per reserved write surface;
- one ACTIVE NOW packet per worker;
- at most one NEXT packet;
- no context switch merely because NEXT exists;
- one authoritative handoff comment per task;
- corrections are deltas, not full duplicate packets;
- worker wakes/polls stop when no actionable owned work remains;
- Fable/L0 owns global transitions/integration/release orchestration.

Do not hard-code today's worker roster into product requirements. Resolve the current owner from the canonical state/inbox map.

## 7. Acceptance path

For member-visible work:
1. frozen North Star packet;
2. implementation owner builds + self-proves truth and parity;
3. independent changed-dependency QA and visual/product review;
4. exact product SHA accepted;
5. exact product integrated;
6. reviewed staging pin;
7. one authorized deploy;
8. hosted changed-journey proof;
9. owner test card;
10. Devin device/feel review.

Do not treat target existence, implementation, test pass, visual pass, integration, staging, hosted verification, and device acceptance as the same state.

## 8. Changed-journey evidence

Every user-visible staging milestone should name the journeys that changed.

Hosted verification should drive those journeys in the environment that can actually reach staging and record:
- served marker;
- setup/fixture;
- actions;
- expected assertions;
- pass/fail/blocked;
- cleanup result;
- screenshot/trace where useful.

A generic site-health check does not replace changed-journey evidence.

If the verification job itself is misconfigured or missing a runtime dependency, the result is failed proof. Do not retry blindly. Fix, review, then re-dispatch under the same release discipline.

## 9. Owner test card

Generate owner review instructions from accepted journey facts, not memory.

Each row should say:
- where to go;
- setup;
- action;
- expected visible result;
- intentional exclusions;
- exact served SHA and rollback SHA.

Do not ask Devin to rediscover basic functional defects that automated/hosted checks could have caught.

## 10. Release gates still load-bearing

Keep separate:
- product source acceptance;
- rules/index readiness;
- callable transport/IAM readiness;
- auth/email runtime readiness;
- shared-device kiosk readiness;
- public-display publication authorization;
- hardware/event operations;
- production authorization.

A release may be visually accepted while one of these remains blocked. Do not translate visual acceptance into "expo ready."

## 11. Current unresolved product decisions

These remain decisions, not implementation defaults:

### Multi-movement goals
Lovable can demonstrate several same-unit movements in one goal. Strategic v3.0 still requires a clearly defined goal/unit. Do not ship a general mixed-movement semantic until Devin explicitly settles the common-unit rule and qualifying-action model.

### Activity catalog
Keep the general community goal/unit catalog separate from the actual FitLife activity menu. Do not infer that a prototype movement is event-approved or that an event shortlist is the complete general product catalog.

### Camera movement vision
R&D only unless explicitly promoted. No automatic credit or verified-exercise claim.
