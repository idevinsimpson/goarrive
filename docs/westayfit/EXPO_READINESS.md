# We Stay Fit — FitLife / LIVE Readiness Contract

Reconciled: September 26, 2026.

This file defines readiness dimensions. It is not a claim that the October 11 activation
is ready. Current state lives in the canonical CURRENT STATE record on #365.

## 1. LIVE product shape

The intended FitLife baseline remains:
- one event community;
- personal phone participation as a complete path;
- two equivalent interactive shared stations/kiosks when hardware/operations permit;
- a separate collective/public display;
- one authoritative contribution/goal state across those surfaces.

LIVE reuses the WSF community product; it is not a separate fake counter/demo product.

## 2. Software readiness

A LIVE release must prove, for the named build:
- approved identity/join path before a credited attempt;
- approved event goal/activity rules;
- stable attempt identity and duplicate protection;
- exact own contribution;
- truthful shared total;
- Living WE progress from confirmed data only;
- goal lifecycle/overshoot/closure behavior;
- phone and independent shared-device convergence;
- pending/unknown/retry behavior;
- disconnection/stale-state behavior;
- no unsupported control presented as working.

Same-browser tabs are not cross-device proof.

## 3. Shared-device privacy readiness

For a kiosk/station:
- sessions are independent;
- the current visitor cannot inherit a previous visitor's identity/receipt;
- Finish/timeout/abandonment clears personal state without clearing event totals;
- browser history/back/cached screens do not expose prior personal data;
- an uncertain prior attempt is reconciled without exposing it to the next person;
- a public QR never grants staff authority or claims the person currently at the kiosk.

Source/test/visual acceptance does not by itself clear unattended/shared-device use.

## 4. Public display readiness

The public display:
- is read-only collective output;
- identifies the actual goal/unit;
- uses publication authorization, not mere membership or goal-id possession;
- defaults to permitted anonymous aggregates;
- shows last-confirmed/freshness state honestly;
- never invents "live" behavior during connection loss;
- does not expose a public member directory.

## 5. Activity readiness

Every real event activity requires approved:
- movement/action definition;
- unit;
- variants;
- instructions/counting;
- repeat rule;
- target/window/time zone;
- equipment/space/hygiene requirements;
- event-appropriate safety review.

A prototype movement is not automatically event-approved.

Keep separate:
- general WSF goal/unit capability;
- the final FitLife movement menu;
- wearable/sensor tracking.

No wearable/automatic step tracking or step equivalents are part of the expo baseline.

## 6. Infrastructure readiness

Verify, rather than infer:
- served build marker;
- callable transport required by the release;
- required Firestore index READY state;
- real verification/reset email behavior where required;
- network/power/device/browser behavior;
- event operator recovery;
- rollback anchor.

A Hosting preview is not an isolated backend.

## 7. Operations/hardware readiness

Devin owns event commitments. Before calling LIVE operationally ready, confirm:
- both kiosk/station devices if retained;
- separate display;
- footprint and movement space;
- power/network;
- transport/setup;
- staffing/support;
- hygiene/equipment;
- organizer permissions;
- co-branding/photo/video permissions where relevant.

Code cannot prove procurement or organizer approval.

They are planning constraints, not readiness evidence.

## 9. Readiness verdict
