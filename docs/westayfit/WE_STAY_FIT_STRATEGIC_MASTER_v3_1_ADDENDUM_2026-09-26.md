# WE STAY FIT — Strategic Master v3.1 Addendum
## Post–September 11 product, visual, and operating decisions
Version 3.1 addendum | September 26, 2026
Owner: Devin Simpson

Status: OWNER-AUTHORIZED DOCUMENT RECONCILIATION. This is a bounded addendum to WE STAY FIT Strategic Master v3.0 — The Living WE System (September 11, 2026). It is not a fourth strategy round and does not reopen the settled Living WE, accounting, privacy, GoArrive-boundary, or brand decisions.

The September 11 master remains the strategic foundation. This addendum governs only the newer decisions and clarifications recorded after it. When this addendum and v3.0 are silent, v3.0 governs. Devin's newer explicit decision still governs its stated scope.

## 1. Why this addendum exists

Since September 11, WSF has gained:
- a formal visual North Star system;
- a persistent member-app shell and route hierarchy;
- journey-specific Lovable reference packets;
- a richer authenticated-community presence/privacy model;
- a bounded real Start-a-community path;
- a more precise release/control-plane model;
- clearer separation between product source, visual reference, hosted evidence, and owner device acceptance.

Those additions sharpen implementation without changing the core strategy:
the community is the enduring product; a goal is its current story; a member's honest contribution changes a trustworthy shared result; the Living WE makes that result visible.

## 3. Lovable has two separate jobs

Do not conflate them.

### Public marketing Lovable
The public WSF marketing/inquiry surface remains a separate Lovable/Supabase lineage. It may own approved public content, inquiries, business pipeline records, and other marketing-side records defined by the architecture.

It is not the active WSF membership/contribution backend.

### North Star Lovable
The "WE Community Home" Lovable project is a design/interaction reference laboratory. It is not a production system of record.

Its job is to make the intended member experience concrete enough to compare, test, and port. Its local/synthetic state is evidence about composition and interaction, not authority for Firebase data, permissions, identity, or accounting.

Do not port:
- localStorage or browser-local authority;
- simulated ledgers or fake server outcomes;
- prototype tools, role switches, scenario selectors, reviewer copy, or sample identities;
- sample totals as real product data;
- unsupported actions simply because a prototype can demonstrate them.

Port the approved experience while preserving canonical truth.

## 4. North Star is an entry gate for member-visible work

Member-visible work does not begin from a vague description and receive visual polish at the end.

Before implementation, freeze a bounded journey packet that includes:
- journey name;
- exact Lovable project/reference SHA or accepted target package;
- states/fixtures;
- required 390×640 and 390×844 evidence, plus affected larger classes where relevant;
- source donor files/tokens when available;
- accepted truth/platform differences;
- navigation, focus, motion, and reduced-motion expectations;
- canonical files reserved for the implementation.

Normal member-visible path:
ACTUAL BEFORE → reviewed/frozen TARGET → implementation → ACTUAL AFTER → independent functional/truth QA → visual/product acceptance → integration → staging → hosted changed-journey proof → owner device/feel verdict.

A green test suite is not a visual verdict. A visual pass is not a backend-readiness proof.

## 5. The app-feel contract

WSF is a mobile-app experience, not a responsive SaaS dashboard.

Avoid:
- long stacks of bordered white/cream cards;
- generic website composition;
- repeated large marketing heroes inside the signed-in app;
- administrative metadata dominating the member view;
- treating the Living WE as a small decorative widget;
- equal visual weight for every secondary action;
- adding more boxes as the default way to introduce hierarchy.

Prefer:
- compact persistent WSF chrome;
- strong selected-community context;
- a dominant, expressive Living WE where progress is the central story;
- layered navy + progress green with purposeful depth;
- strong iconography and typography hierarchy;
- one obvious primary movement action;
- sheets/focus flows for bounded tasks;
- restrained secondary surfaces;
- truthful human presence where permitted;
- reachable controls on short phones, with keyboard and safe-area behavior considered.

Motion explains cause and effect. It does not simulate activity. Preserve reduced-motion behavior and never delay a usable screen for animation.

## 6. The member shell is product direction

The primary member spaces are:
- Home
- Community
- Progress
- You

MOVE is a focused action flow over the member context, not a fifth tab.

Settings is a utility surface, not a primary member destination.

Preserve:
- mounted tab context where the current shell supports it;
- meaningful back/close destinations;
- tab state and scroll continuity where supported;
- focus return for keyboard/assistive-technology users;
- explicit cold/deep-link fallbacks;
- kiosk exclusion from the ordinary personal-device member shell.

Do not "simplify" this back into a sequence of unrelated website pages without an explicit product decision.

## 7. Surface jobs

### Home
The heartbeat of the selected community:
- community identity and truthful presence;
- current/featured eligible goal;
- dominant Living WE and exact progress;
- clear MOVE action;
- exact own part where available;
- restrained recent momentum;
- freshness/recovery state when material.

Home should answer: where are we, what can I do, and can I see that my part matters?

### Community
Belonging and people:
- selected community identity and facts;
- membership/role context;
- current goals and history;
- member/community context;
- Champion actions only when the member actually has the required authority.

Do not turn Community into a generic admin dashboard.

### Progress
The member's private record:
- exact own contributions;
- goal/unit-specific history;
- truthful shared context where authorized;
- no rankings, streak pressure, blended score, or implication that another person's work is mine.

### You
Member identity and belonging:
- selected-community membership/role;
- meaningful own contribution context;
- account actions and utility links;
- privacy/settings remain a utility, not the main identity experience.

## 8. Authenticated community presence and privacy

Public-display privacy and authenticated-community visibility are different contexts.

The authenticated member experience may show truthful community presence and recent movement when permitted. The current social direction includes:
- community-visible member presence for active members;
- recent community momentum;
- per-community "show my name" / "show my contributions" choices;
- explicit privacy choices that survive ordinary membership continuity;
- no Champion override of a member's privacy choice;
- no email, phone, token, or private-contact exposure.

"Community-visible by default" never means:
- internet-public;
- public-display-visible;
- kiosk-visible;
- marketing-public;
- publication permission.

Public displays still default to permitted aggregates, not member identity.

Membership access, community visibility, and publication authority remain separate.

## 9. Start, join, and continuation

Joining remains as legitimate as starting.

Newer implementation direction brings a bounded real community-launch path into the first useful product:
- signed-in eligible member;
- Start a community;
- smallest approved community identity/admission setup;
- one approved goal/activity configuration with positive target and published window/time zone;
- trusted Founding Champion membership assignment for that community only;
- working invitation/join path;
- another account can actually join and contribute.

This does not authorize:
- general geographic discovery;
- a full Champion administration platform;
- organization self-verification;
- contact imports;
- payments;
- broad automation;
- a second membership backend.

A community works without a prize, kiosk, queue, coach purchase, or organization contract.

## 10. Goal composition remains truth-first

Different movements CAN contribute to the same defined community goal and therefore share the same Living WE percentage. This explicitly supersedes any earlier reading that each unlike movement must necessarily have its own WE.

The percentage belongs to the shared goal. A multi-movement goal must state what the target measures and which movements/actions qualify so members can understand exactly how each valid contribution advances that one shared result.

Different movement names do not require separate percentages or separate WEs. Measurement truth still matters: do not silently blend unlike units or invent equivalents unless an explicit approved rule defines a truthful common unit or conversion. Hold seconds, repetitions, laps, manually recorded steps, and custom count units remain semantically distinct unless such a rule exists.

Distinguish:
- the general community goal/unit catalog;
- the approved FitLife event activity menu;
- sensor/wearable step tracking.

The expo baseline still excludes wearable/automatic step tracking and step equivalents.

## 11. Contribution/reward moments consume canonical truth

Emotional payoff must not become a second truth system.

Contribution confirmation begins after an authoritative receipt. Own amount remains separate from shared change. A lost reply/replay may acknowledge that the same attempt was counted once without creating another contribution.

Goal-reached celebration is tied to the authoritative goal event/current state and must not replay merely because a screen reloads.

Milestone moments may be shown only from authoritative before/after state available to that surface; do not attribute a group milestone to one member unless the record proves it.

No reward/points ledger is authorized by this addendum.

## 12. LIVE remains the same product truth on different surfaces

Phone is a complete personal participation surface.

Kiosk/station is an optional shared interaction surface and must have explicit session/privacy handling.

Large/public display is a read-only collective surface with publication authorization and anonymous aggregate defaults.

The same goal/contribution accounting governs all surfaces. Do not create independent counters per device.

Shared/unattended kiosk use requires its own device/privacy/recovery evidence. Source acceptance alone does not clear it.

## 13. Operating discipline now required

Use the current Fable operating protocol and canonical worker inboxes.

Core rules:
- one implementation owner per write surface/workflow;
- one ACTIVE NOW packet per worker;
- at most one NEXT packet;
- one authoritative handoff per task;
- no duplicate full packets;
- no-op sweeps stay silent;
- worker polling stops when no actionable owned work remains;
- critical-path member-visible work outranks scale/control-plane work unless the latter blocks truth, privacy, data integrity, cross-device behavior, or release safety.

Keep evidence labels separate:
SOURCE INSPECTED · IMPLEMENTER REPORTED · TEST VERIFIED · VISUAL VERIFIED · DEPLOYMENT RECEIPT · HOSTED VERIFIED · DEVICE VERIFIED · OWNER ACCEPTED.

## 14. Release/control-plane clarification

A reviewed staging pin identifies what may be deployed; it is not itself a deployment.

A build is not a hosted pass. A generic hosted 200 is not journey proof.

Member-visible releases should carry a machine-readable changed-journey manifest and, once the accepted tooling is active, a hosted changed-journey result plus owner test card.

The human pin gate stays in force until an explicit later decision changes it.

A failed activation/smoke run that creates nothing and changes nothing is a failed proof, not a degraded-but-passed release.

## 15. R&D stays isolated until adopted

Camera/vision-assisted movement counting is currently R&D only unless a later explicit product decision integrates it.

Do not infer:
- automatic contribution credit;
- verified exercise;
- health/fitness accuracy claims;
- production camera collection;
- storage of video/frames;
- Expo/native readiness.

No R&D prototype silently changes the production activity contract.

## 16. Unchanged v3.0 foundations

This addendum does not change:
- the exact primary tagline or supporting line;
- community as the enduring product;
- Living WE as truthful goal progress;
- fixed targets, overshoot, rounding, near-goal and lifecycle rules;
- no fake momentum/decay/premature 100%;
- sharing/recruiting/coaching as optional;
- privacy/publication separation;
- under-13/youth-specific exclusions and the prohibition on silently reinstating an 18+ gate;
- GoArrive's ownership of individualized coaching;
- no dual active community/contribution system;
- no production release without the required authority.
